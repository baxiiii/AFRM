## 1. Why it is needed

The baseline (`v1.0.1`) contains 35 tests. Two of them, `Calculations.REQ_WEIGHT_00_AircraftWeightDoesNotAffectFuelCalculation` and `Assessment.REQ_WEIGHT_00_AircraftWeightDoesNotAffectFuelAssessment`, characterise how the model treats aircraft size. Both pass, and a pass shows the limitation: two records built for hypothetical 5,000 kg and 100,000 kg aircraft give identical fuel values, status and explanation, because the model has no weight input.

Two consequences follow:

1. Each record carries its own cruise and holding flow and the code uses them as given. Nothing ties an aircraft's size to its fuel burn, so a user must work out the right flows by hand for each type, and a wrong figure goes unnoticed.
2. The test data covers one size of aircraft only. Across all 27 baseline records, cruise flow is roughly 2,200 to 2,650 kg/h and holding flow roughly 2,000 to 2,400 kg/h. The threshold logic has therefore never been exercised at a very small or very large burn scale.

CR-001 adds three weight classes that scale the burn, so the same flight geometry and fuel load give different, traceable results for different aircraft. It also lets the test suite exercise the assessment thresholds at three scales. This improves the existing application. It is not a defect fix.

## 2. The change

Each flight record gains an `aircraft_weight_kg` value. Only three values are supported, and each maps to a class and a burn multiplier:

| Class | `aircraft_weight_kg` | Burn multiplier |
|---|---|---|
| LIGHT | 5000 | 0.25 |
| MEDIUM | 20000 | 1.0 |
| HEAVY | 100000 | 5.0 |

The multipliers are fictional values chosen to keep results easy to check by hand. They are not real aircraft data.

For each record, the effective flows are:

- effective cruise flow = `cruise_flow_kg_per_hour` × multiplier
- effective holding flow = `holding_flow_kg_per_hour` × multiplier

Everything else in `calculate_fuel()` is unchanged but now uses the effective flows: trip fuel to go, alternate fuel, contingency (greater of 5% of trip fuel or five minutes at holding flow), final reserve (30 minutes at holding flow), and PFD. The status thresholds, rounding rules and `>=` comparisons are unchanged.

**Requirement R6 (`REQ_WEIGHT_01`):** Cruise and holding flow are scaled by the multiplier for the record's weight class before fuel is calculated, and contingency, alternate fuel, final reserve and status follow from the scaled values. MEDIUM leaves every result unchanged.

**Requirement R7 (`REQ_WEIGHT_02`):** The CSV has a ninth column `aircraft_weight_kg` and accepts only 5000, 20000 and 100000. Any other value, a blank, or a non-numeric entry rejects that row with its line number and reason, and loading continues. A file with the old eight-column header is rejected as a whole.

The new CSV header is:

`flight_id,trip_distance_nm,alternate_distance_nm,distance_flown_nm,fuel_on_board_kg,ground_speed_knots,cruise_flow_kg_per_hour,holding_flow_kg_per_hour,aircraft_weight_kg`

## 3. Why `v2.0.0`

The loader rejects the `v1.0.1` file format, so existing data files stop loading until a ninth column is added. That is a breaking change, so the major version number increases.

## 5. Hand-worked check values

All use the boundary flight geometry from `BND-01`: trip distance 1000 nm, distance flown 400 nm, alternate distance 200 nm, ground speed 400 knots. The base flows are 2400 kg/h cruise and 2160 kg/h holding.

Remaining distance is 600 nm, so trip time is 1.5 h and alternate time is 0.5 h.

| | LIGHT (×0.25) | MEDIUM (×1.0) | HEAVY (×5.0) |
|---|---|---|---|
| Cruise flow (kg/h) | 600 | 2400 | 12000 |
| Holding flow (kg/h) | 540 | 2160 | 10800 |
| Trip fuel to go (kg) | 900 | 3600 | 18000 |
| Alternate fuel (kg) | 300 | 1200 | 6000 |
| Contingency (kg), greater of 5% trip fuel or 5 min holding | 45 | 180 | 900 |
| Final reserve, 30 min holding (kg) | 270 | 1080 | 5400 |
| Protected fuel (kg) | 615 | 2460 | 12300 |
| Fuel on board for NOMINAL threshold (kg) | 1515 | 6060 | 30300 |
| Status at that fuel on board | NOMINAL | NOMINAL | NOMINAL |
| Status at one kilogram less | CAUTION | CAUTION | CAUTION |

Same record, same fuel on board of 6060 kg, different class:

| Class | PFD (kg) | Status |
|---|---|---|
| LIGHT | 5160 | NOMINAL |
| MEDIUM | 2460 | NOMINAL |
| HEAVY | -11940 | FUEL EMERGENCY |

The MEDIUM column matches `BND-01` and `BND-02` in the baseline data, which is the regression anchor.

## 6. Acceptance tests

These 11 tests are written and committed **before** any implementation, with stub functions so they fail on assertions and not on compile errors. CI is expected to fail on that commit, and that run is kept as evidence.

| Test | Pass if |
|---|---|
| `Calculations.REQ_WEIGHT_01_MediumMatchesBaseline` | MEDIUM results equal `v1.0.1` for every baseline record |
| `Calculations.REQ_WEIGHT_01_LightAndHeavyScaleBothFlows` | Flows match section 5 for LIGHT and HEAVY |
| `Calculations.REQ_WEIGHT_01_ReservesFollowClass` | Contingency, alternate and final reserve match section 5 |
| `Assessment.REQ_WEIGHT_01_ThresholdsExactAtEachClass` | NOMINAL at 1515, 6060 and 30300 kg and CAUTION one kilogram below |
| `Assessment.REQ_WEIGHT_01_SameFlightDifferentStatusByClass` | 6060 kg gives NOMINAL, NOMINAL, FUEL EMERGENCY for LIGHT, MEDIUM, HEAVY |
| `CsvLoader.REQ_WEIGHT_02_ValidWeightsLoaded` | 5000, 20000 and 100000 load |
| `CsvLoader.REQ_WEIGHT_02_UnsupportedWeightRejectedWithLineAndReason` | Other, blank and non-numeric weights reject only that row |
| `CsvLoader.REQ_WEIGHT_02_NineColumnHeaderRequired` | The nine-column header is accepted |
| `CsvLoader.REQ_WEIGHT_02_EightColumnFileRejected` | The old header rejects the whole file with a clear error |

## 7. Risks

| Risk | Mitigation |
|---|---|
| Multiplier applied to only one flow, so reserves and trip fuel disagree | Tests check both flows and every derived quantity against hand values |
| A mapping error treats an unsupported weight as MEDIUM | Loader rejects unsupported values, with a dedicated test |
| Breaking the baseline results | MEDIUM regression test and byte comparison |
| Multipliers mistaken for real aircraft data | Documented as fictional in the README and this CR |
| More code to maintain | The change is confined to model, config, calculation, loader and generator |
| Regenerated data hides a threshold error | Boundary records are built from hand-worked values, not from the code under test |
